# Audit 360° — titisite (baptiste-niszczota.com)

**Date** : 12 juin 2026 · **Périmètre** : intégralité du dépôt (~32 200 lignes JS/JSX), configuration de déploiement, CI, dépendances.
**Méthode** : revue de code exhaustive (4 passes parallèles : sécurité backend, qualité frontend, perf/SEO/UX, DevOps/dépendances) + build de production réel + `npm audit`.

> Calibrage : ce site est un **portfolio personnel + outil de gestion de projets privé + espace d'écriture créative**, pas un produit commercial. Les notes CRO/Business/IA sont à lire dans ce contexte — les recommandations « croissance » sont volontairement proportionnées.

---

## PHASE 1 — Compréhension globale du projet

**Ce que fait le site.** Application Node mono-processus à trois visages :
1. **Portfolio public** (`/`) : hero, projets, musique (extraits 30 s), photos, CV (formation/expérience), contact — contenu éditable via un CMS maison (`/admin`).
2. **Espace de travail privé** (`/project/*`) : kanban de features, réunions + export iCal, documents, builds de jeu (jusqu'à 1 Go), scopé par workspace avec rôles admin/member.
3. **Espace d'écriture** (`/projets/ecriture/*`) : univers → livres → chapitres, lecteur avec bande-son, personnages, glossaire, cartes 3D voxel façon Minecraft (three.js) et atlas 2D.

**Pour qui.** Le propriétaire (vitrine professionnelle + outil personnel) et un cercle restreint de collaborateurs/lecteurs. Public cible de la vitrine : recruteurs, clients potentiels, communauté créative.

**Points forts business** : différenciation forte (la carte voxel et le lecteur immersif sont des démonstrations de compétence en soi — le site *est* le portfolio), stack 100 % maîtrisée, coût d'exploitation quasi nul (un VPS, SQLite).
**Points faibles business** : la partie la plus impressionnante (écriture/cartes) est invisible des moteurs de recherche et des aperçus sociaux (SPA sans SSR, sitemap réduit à la home) ; pas de capture de contact structurée (mailto uniquement) ; aucune mesure de disponibilité.
**Risques business** : perte totale de données (aucune sauvegarde du SQLite ni des uploads — voir Phase 9) ; dépendance à une seule machine ; image dégradée si un recruteur partage le lien et obtient un aperçu social vide.

**Note Phase 1 : 7/10** (proposition de valeur claire et différenciante, mais sous-exploitée faute de visibilité).

## PHASE 2 — Architecture

### Ce qui est bien conçu
- Monolithe assumé et cohérent : Express sert l'API et la SPA buildée ; SQLite WAL + FK activées (`server/db.js`), instance PM2 unique en mode fork — le seul choix sûr avec better-sqlite3.
- Séparation nette : `server/routes/*` (1 fichier/ressource), middleware de scoping workspace (`server/middleware/scope.js`) qui rend l'IDOR inter-workspace structurellement impossible, routeur générique `collection.js` pour les collections JSON-blob.
- Conventions documentées et respectées (CLAUDE.md à jour, `api.ws(slug)` côté client, primitives UI partagées).
- Pattern « lazy-prepare » des statements SQL documenté après incident (bonne culture du post-mortem).

### Problèmes identifiés

## PHASE 3 — Code

### Synthèse
Codebase **saine** : nettoyage des event listeners systématique (vérifié sur EmojiPicker, CursorEffect, AmbientCanvas, ReaderAudio, Reader), inputs tous contrôlés, dépendances des `useEffect` correctes sur l'échantillon audité, renderer Markdown maison **sans surface XSS** (`safeHref()` rejette `javascript:`, aucun `dangerouslySetInnerHTML`, regex recréées à chaque appel pour éviter la pollution de `lastIndex`).

### Top des problèmes de code (classés)

**Élevé**
1. Aucune ErrorBoundary (cf. A1).
2. **Fuites GPU three.js** : `VoxelTerrain.jsx:35-40` — géométries/textures créées en `useMemo` jamais `dispose()` ; dans les éditeurs de carte (MapEditor, TerrainPainter), chaque modification de terrain abandonne l'ancienne géométrie en mémoire GPU. Correctif : `useEffect(() => () => terrainGeo?.dispose?.(), [terrainGeo])`.
3. Pas de focus-trap dans `Modal` (`src/components/project/shared.jsx:68-106`) : la navigation clavier s'échappe derrière la modale (WCAG 2.4.3).
4. Composants-dieux (cf. A2).

**Moyen**
5. `src/api/client.js` : pas d'AbortController — les requêtes obsolètes ne sont pas annulées (réponses périmées possibles en navigation rapide).
6. `CursorEffect.jsx` : handler `mousemove` non throttlé par rAF (100+ événements/s).
7. `prefers-reduced-motion` respecté en CSS (`styles.css:514-523`) et dans PhotoCarousel, mais **ignoré** par AmbientCanvas et CursorEffect — seul le bouton pause manuel (`window.__animPaused`) existe.
8. Boutons sans `type="button"` (dont le bouton fermer de Modal, `shared.jsx:60`) → submit involontaire à proximité d'un formulaire.
9. i18n partielle : fr/en/ko couverts pour le public, mais chaînes FR en dur dans `Stairs.jsx:23,27`, `ProjectDetailPage.jsx:88` (« 404 — projet introuvable »), `Kanban.jsx:70` ; admin FR-only (acceptable, à documenter).
10. `TagsPopup.jsx:17-23` : setTimeout sans clear (course bénigne).
11. Duplication des patterns formulaire/confirmation/drag&drop entre Kanban, Minecraft et les éditeurs de carte.
12. `effects.jsx`/`Scene.jsx` (map) : créations d'objets THREE par render évitables.

**Faible**
13–20. Code mort mineur (A7), styles inline (A4), absence de cache (A5), `AnalyticsEditor` double-fetch spammable, mutations de style au hover, `document.body.style.cursor='none'` dans CursorEffect, prop drilling léger dans ProjectLayout (acceptable), absence de tests unitaires frontend.

### Top 10 refactorisations prioritaires
1. ErrorBoundary root (0,5 h, impact élevé) · 2. Disposal three.js (1 h, élevé) · 3. Hook `useItemList` (2 h) · 4. Focus-trap Modal (1 h) · 5. AbortController dans client.js (1,5 h) · 6. Découpage des composants-dieux (4 h) · 7. `prefers-reduced-motion` dans les effets ambiants (0,5 h) · 8. Audit `type="button"` (1 h) · 9. Throttle rAF du CursorEffect (0,5 h) · 10. Cache ProjectDetailPage (1 h).

**Note Code : 7,5/10**

## PHASE 4 — Performance

### Mesures réelles (build de production exécuté)
- **JS total : ~1,8 Mo (≈500 Ko gzip)** ; CSS : 22,7 Ko (8,5 Ko gzip).
- Chunk dominant : **`Scene-*.js` = 879 Ko (236 Ko gzip)** — three.js + fiber + drei + moteur voxel. Importé *statiquement* par `ProjectPage` → embarqué dans le chunk Écriture au lieu d'être chargé à la demande.
- Entrée `index-*.js` : 143 Ko (47 Ko gzip) — correct. 7 chunks de route distincts via `React.lazy` — bon réflexe déjà en place.
- `vite.config.js` : **aucun `manualChunks`** — le découpage repose sur les heuristiques par défaut.

### Problèmes et correctifs (matrice impact/effort)

**Impact élevé / effort faible**
| Problème | Fichier | Correctif | Gain |
|---|---|---|---|

| Pas de `Cache-Control` sur `/api/images/*` et `/api/audio/*` (noms UUID immuables) | `server/index.js:185-210` | `res.set('Cache-Control','public, max-age=31536000, immutable')` avant `sendFile` | Images re-validées à chaque visite aujourd'hui |

## PHASE 5 — SEO

### Constat central (critique)
SPA sans SSR ni pré-rendu : le HTML livré est `<div id="root"></div>`. Googlebot exécute le JS, mais : **aucun aperçu social** pour les pages projet/écriture, pas de `og:image` même sur la home (le TODO du repo le sait), **sitemap limité à la seule home** (`public/sitemap.xml` — le commentaire du fichier reconnaît le manque), **aucune balise canonical**, **aucun JSON-LD**, pas de `document.title` dynamique par route vérifiable, pas de hreflang malgré 3 langues (fr/en/ko en localStorage — invisible pour les moteurs).

**Bien en place** : title/description/OG/Twitter corrects sur la home, `lang="fr"`, robots.txt propre (bloque /admin, /project, /api), redirection www→apex et HTTP→HTTPS (pas de duplication), HSTS.

### Top améliorations SEO (ordre de priorité)
1. **og:image 1200×630** sur la home (déjà documenté dans TODO — 1 h, gain immédiat sur chaque partage).
2. **Sitemap dynamique** servi par Express depuis la DB (projets + univers d'écriture + /photos) — ~2 h, gabarit fourni par la route `settings.js` existante.
3. **JSON-LD `Person`** (+ `CreativeWork` par projet) dans `index.html` — 1 h.
4. `<link rel="canonical">` statique sur la home + gestion dynamique par route — 2 h.
5. `document.title` + meta description par route (hook `usePageMeta`) — 2 h.
6. **Pré-rendu build-time** des routes publiques (home, /photos, pages univers) — le vrai déblocage de l'indexation du contenu ; ~20 h ou via un middleware Express qui injecte title/OG/JSON-LD par route (~4 h pour 80 % du bénéfice).
7. hreflang seulement si les langues deviennent des URLs (`?lang=` ou `/en/`) — sinon sans objet.
8. Alt text systématique sur les images de projets (audit rapide), maillage interne home → pages écriture (liens HTML réels, déjà le cas via react-router — vérifier qu'ils sont des `<a href>`).
9. Soumettre le sitemap à la Search Console + suivre la couverture d'indexation.
10. Contenu : les pages univers/personnages sont un gisement de longue traîne (worldbuilding) totalement non indexé aujourd'hui.

**Note SEO : 4/10**

## PHASE 7 — CRO (calibré portfolio)
Il n'y a ni tunnel de vente ni pricing : la « conversion » = prise de contact + consultation des projets.

3. Ajouter un **lien CV téléchargeable** (PDF) près du CTA contact.
4. Preuve sociale : liens GitHub/LinkedIn présents — ajouter des liens « voir en ligne » par projet quand ils existent.

## PHASE 8 — Sécurité (le point fort du projet)

### Verdict d'ensemble
Posture **nettement au-dessus de la moyenne** pour un projet personnel. Aucune vulnérabilité critique exploitable identifiée dans le code applicatif. Les « bonnes pratiques OWASP » sont largement couvertes et — fait rare — **testées en CI** (`test/security.test.js` : headers, CORS, révocation JWT, RBAC ; gitleaks + semgrep + npm audit dans `.github/workflows/security.yml`).

**Vérifié sain** : 100 % des requêtes SQL paramétrées (aucune concaténation trouvée) ; bcrypt 10 rounds ; JWT en cookie HttpOnly `SameSite=Strict` (+ `Secure` en prod) avec **blocklist de révocation** et `token_version` ; rate-limit login persistant en SQLite (insensible au restart) ; uploads à double allowlist MIME+extension, noms UUID, multer borné (50 Mo/100 Mo/1 Go) ; `/api/audio` et `/api/images` cross-checkés contre la DB (pas de fuite de `uploads/`) ; regex anti-traversal sur les filenames ; CSP stricte (`script-src 'self'`), HSTS, frameAncestors none, Permissions-Policy ; CORS désactivé en prod ; `CANONICAL_ORIGIN` obligatoire en prod (anti Host-header injection sur les URLs iCal) ; access_log coupé sur `/api/calendar/` ; analytics sans IP brute (hash journalier) ; erreurs 500 sans stack trace ; secretlint en pre-commit ; **historique git propre** (jamais de .env/sqlite/uploads commités — vérifié sur les 58 commits).

## PHASE 11 — Positionnement
**Pourquoi un visiteur/recruteur retient ce site** : démonstration technique vivante (cartes voxel, lecteur immersif, CMS maison, sécurité au-dessus du lot pour un portfolio) ; identité visuelle forte ; trilinguisme.
**Pourquoi il passerait à côté** : il ne le trouve pas (SEO), l'aperçu partagé est vide (OG), le premier chargement est lourd sur mobile (500 Ko gzip), et rien ne l'incite à laisser une trace (mailto).
**Différenciation vs portfolios template (Webflow/Framer)** : nettement supérieur en profondeur, inférieur en finition SEO/social — exactement l'inverse de ce qui est difficile à rattraper. Les correctifs SEO sont peu coûteux ; la profondeur, elle, ne s'achète pas.
